# 采用方上下文自动加载：install 写入 .codebuddy/rules 总是类规则 — architecture 005 / 目标架构 v0.5

> **状态：待执行（planned）。** 本计划修复 Q25/Q26 暴露的核心缺口：当前 `install-standard` 只写入 hook（强制门），**不向 agent 注入规范上下文**——agent 是否照规范行事完全取决于它"碰巧"是否读到 `README.md`/`workflow.md`。经 Q26 对 CodeBuddy 加载架构的实证调查，决定采用 **`.codebuddy/rules` 的「总是」类规则（`alwaysApply: true`）** 作为上下文自动加载载体，并确立**重名强制替代**默认策略。聚合来源见 `questions/025.md`（context 不能保证）+ `questions/026.md`（CodeBuddy 加载架构调查，结论选 rules）。本文件即框架 v0.5 的权威计划；`architecture_index.json` 的 `latest_version` 升 5，`implemented_version` 待执行后置 5。

---

## 0. 背景与问题

- **Q25 发现**：装完后 agent 正常 prompting 时，规范上下文**不会**被自动加载；`install` 只 wiring hook（强制门），不注入任何文档。
- **Q26 调查（实证）CodeBuddy 加载架构**：
  - `CODEBUDDY.md` / `AGENTS.md`（根目录）：**默认全文注入**上下文（类 CLAUDE.md）。
  - `.codebuddy/rules`：每条规则是**文件夹 + `RULE.mdc` + frontmatter**；分三类——**总是**(`alwaysApply:true`，新会话开始注入原文、全程生效)、智能体请求(`false`，仅注入名称+描述、agent 判相关时自读)、手动(需 `@`)。
  - `.codebuddy/skills`：元数据常驻、场景匹配自动触发。
  - **hooks**：Overview / Rules / Skills 公开文档**完全未记载**，无法保证 IDE 执行 `.codebuddy/settings.json` 里的 hooks。
  - **致命限定**：自动加载仅在**会话开始**发生一次；改/增规则后须**新建会话**才生效。

---

## 1. 决策与理由（为何选 rules 而非 CODEBUDDY.md / skills）

1. **选 `.codebuddy/rules`（总是类）而非 `CODEBUDDY.md`**：`CODEBUDDY.md` 几乎是现代项目的**标配**，install 时大概率已存在，写入会被忽略或冲突；而 rules 用**专属命名空间**（`ai-project-standard`）大概率避免重名。即便运气不好真重名（典型：装新版本规范发现旧版本 rule 残留），按本版默认策略**强制替代**（见 §4）。
2. **选「总是」(`alwaysApply: true`)**：保证每个**新会话开始**把规则原文注入上下文开头，agent 始终知道本规范存在、并在改受管文件前先读 `README.md`/`workflow.md` 按规记录——这是"保证加载"的唯一文档可证实路径。
3. **保留 hooks 不移除**：hooks 继续作为强制门（漏记 `exit 2`）。Q26 指出其公开文档未背书，v0.5 **不赌它 alone**，而是用 rules 补上上下文保障；并在 install 输出提示"新建会话后规则生效；hooks 是否触发请实测"。
4. **不首选 skills 载体**：skills 元数据虽常驻，但其正文靠 `description` 场景匹配才触发，不如"总是"类规则直接全文注入可靠；rules 是本次最小且最确定的修复。

## 2. 规则文件规范（遵循 CodeBuddy Rules）

- **路径**：`<project>/.codebuddy/rules/ai-project-standard/RULE.mdc`
- **格式**（frontmatter 必需字段，遵循官方 Rules 规范）：
  ```yaml
  ---
  description: AI Project Standard (ai-project-standard) — 本项目采用的项目规范框架；凡改动受管文件前必须先读其 README/workflow 并按"任何改动进 history"强制门记录。Use when editing architecture/、*_index.json、questions/、issues/、improvements/、README.md、references/、scripts/、skills/、assets/、standard_version、.codebuddy/settings.json。
  alwaysApply: true
  enabled: true
  updatedAt: <ISO8601>
  provider:
  ---
  ```
- **正文**：以 `<system_reminder>` 包裹（与插件规则规范一致），指示 agent：
  - 本项目采用 `ai-project-standard` v0.5（`install-standard` 写入）。
  - 受管文件清单：`architecture/`、`*_index.json`、`*_TOC.md`、`questions/`、`issues/`、`improvements/`、`README.md`、`references/`、`scripts/`、`skills/`、`assets/`、`standard_version`、`.codebuddy/settings.json`。
  - 任何对上述文件的改动**必须**在 `history/` 留痕（见 `<README路径>/README.md` 的「MANDATORY」节与 `references/workflow.md`）；提问双录 `questions/` + `qna_recorded`；改进进 `improvements/`。
  - **路径随 install_mode 自适应**：copy 模式指向 `<project>/.plan-standard/README.md`；self 模式（框架仓库自举）指向 `<repo>/README.md`。
- **updatedAt**：写入时置当前 ISO8601，便于 upgrade 时判新旧。

## 4. 重名 / 替换策略（默认强制替代）

- **默认方法 = 强制替代（force replace）**：若目标 `<project>/.codebuddy/rules/ai-project-standard/` 已存在（典型场景：用新版本规范重装项目，发现旧版本 rule 残留），`install-standard` / `update-standard` **直接覆盖写**该 `RULE.mdc`，不询问、不合并。
- **理由**：采用方任一项目只应持有**一个**规范版本；旧 rule 属被取代对象，无保留价值。命名空间 `ai-project-standard` 已大概率避免与项目既有规则冲突；万一冲突（即本项目恰好已用同名命名空间做别的事），仍以规范 rule 为准覆盖——这是可接受的明确默认。
- 不做备份/重命名（如 `ai-project-standard.old`）——保持"单版本真相"。如未来需要保留旧 rule，属非默认场景，由人工介入。

---

## 5. 会话生效限制（必须提示）

CodeBuddy 规则**仅在会话开始**注入一次；install/update 后**必须新建会话**规则才生效。这是平台硬限制，无法绕过。install/standard 输出与 `README.md` 安装说明须**醒目提示**此点，避免用户以为装完当即生效。
