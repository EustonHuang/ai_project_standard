## 0. 背景与目标

当前这套东西从「记历史的 skill」长成了「一切项目该怎么记历史」的强制约定，且自身也用同一套格式记历史（dogfooding）。由此引发三个认知纠偏（Q21–Q23）：

1. **它不是一个 skill，而是一套「项目规范框架」（元规范 metastandard）。** `skill` 暗示「某 workspace 的 `.codebuddy/skills` 下一份可选能力」；但本项目定义的是跨项目的强制约定，且自我套用。故应**改名定位**，并把它从 `.codebuddy/skills/` 搬出。
2. **它不是全局强制，而是「可选采用」。别人的项目可以不采用**（他们有自己的框架）；而我自己的项目应当采用。采用方只需持有一份**版本指针（锁文件）**，不持有框架副本；框架提供工具查询「最新版本」并在采用方落后时告警。
3. **规范自身也必须被版本控制。** 当前 002 的内容已被覆盖、追溯靠考古——根因是没有对「规范自身」做 git 版本控制。从本版起，框架仓库每次版本 bump 必须 commit + push 到远程，每个 `architecture/NNN.md` 打 tag。

本计划四大块工作：① 定位重定义 + 双版本轴；② 独立 git/GitHub 仓库 + 迁移；③ 内置 `install/update/check` skills；④ improvements 栏目 + README 改名 + 追问流程修正。

## 1. 定位重定义：skill → 项目规范框架

### 1.1 是什么 / 不是什么
- **是**：一套定义「项目怎么记历史 / 怎么提问题 / 怎么留故障 / 怎么提改进 / 怎么被门禁强制留痕」的**项目规范框架**。任何项目可声明采用它，并据此获得一套一致的记录结构与强制门。
- **不是**：一个塞在 `.codebuddy/skills/` 下的 skill。它的载体是**独立的 git 仓库**，不是某个 workspace 的 skills 子目录。
- **可选采用**：我自己的项目采用；别人的项目可不适用（他们有各自框架）。采用方通过 `install-standard` 获得本框架，并在落后时被告警。

### 1.2 两条版本轴（核心，必须区分）
- **轴 A — 规范版本轴 `standard_version`**：项目「所用框架的版本」，如 `v0.4`。每个采用方项目在根目录声明一份轻量锁文件（建议 `.plan-standard/version` 或 `project_standard.json`，含 `standard_version` + `pinned`）。
- **轴 B — 项目自身版本轴**：项目**领域**的迭代（如某项目的 wiki schema 版本、某产品的 release 版本）。项目自己的 `architecture/` 放的是**项目领域**的设计版本（v1/v2…），用其 `architecture_index.json` 的 `implemented/latest_version` 跟踪。

> **关键区分**：在**框架仓库自身**，它的 `architecture/001..004.md` 既是「框架的规范版本（轴 A）」也是「框架的领域内容（轴 B）」——二者重合，注明即可，框架自身 `standard_version = 最新`。
> 在**采用方项目**，`architecture_index.json` 的 `implemented/latest_version` 描述的是**该项目领域版本（轴 B）**；而「它用哪版框架（轴 A）」另记在 `standard_version` 锁文件里。两者切勿混写。

## 3. 内置 skills（放在 `ai_project_standard/skills/` 下）

框架仓库自带作用于采用方项目的技能。每个 skill 是标准 CodeBuddy skill 形态（含 `SKILL.md`）。

### 3.1 `install-standard <version> <project>`
1. 检出框架指定 tag（如 `v0.4`）到采用方可引用位置（见 §7.2）：拷贝到 `<project>/.plan-standard/`，或引用统一本地安装目录。
2. 把 hook 配置写入采用方 `<project>/.codebuddy/settings.json`（Stop/UserPromptSubmit/PostToolUse 钩子指向已安装框架的 `scripts/turn_gate.py`）。
3. 写采用方 `standard_version` 锁文件（`standard_version=<version>`、`pinned=...`）。
4. 脚手架出采用方的 `history/` `questions/` `issues/` `improvements/` 目录与 `*_index.json` / `*_TOC.md` 模板。
5. 报告安装结果与当前框架版本。

### 3.2 `update-standard <project> [--to latest|<version>]`
1. 读采用方锁文件得当前 `standard_version`。
2. 比对 latest（框架仓库 tag / `architecture_index.latest_version`）。
3. **同 major**：自动升级——更新锁文件、必要时更新 hook、拉取新脚本。
4. **跨 major（breaking）**：先跑 **breaking-change review**（列出两版本间 `architecture` diff 与破坏性项，见 §4），须 `--confirm-breaking` 且要求**人工 review 输出**后才动 hook / 锁文件。
5. 升级后输出「已从 vX.Y → vA.B」。

### 3.3 `check-standard <project>`
输出：当前版本 / 最新版本 / 是否落后 / 有无可用更新；若采用方 `improvements/` 有未实施项，一并报告条数（可选）。

## 4. breaking-change 策略（类 semver）

- 每个 `architecture/NNN.md` 头部声明：
  - `version: v<major>.<minor>`
  - `breaking: true | false`
  - `breaking_items: [...]`（相对上一版的破坏性项，如「目录改名 X→Y」「hook 配置字段变更」）。
- `update-standard` 逻辑：
  - 同 major（minor 变化）：向后兼容，自动升级。
  - 跨 major：非向后兼容，**须 `--confirm-breaking` + 人工 review** 才执行；review 输出（哪些文件/结构会变）须被记录。
- 任何 `improvements` 被 implement 时若改变既有结构，须在该 `architecture` doc 标 `breaking: true`。

## 5. improvements 栏目（规范改进队列）

与 `history/`、`questions/` 平行，用于把「一时做不了的改进」进队列，等有空再做，形成**规范改进流程**（不再要求每次改进都立刻看、立刻加进计划）。

### 5.1 结构
```
ai_project_standard/
  improvements/<zeroed_id>.md      # 一条改进建议（内容可改）
  improvement_index.json           # max_id / revision / briefs
  improvement_TOC.md               # 从 index 派生（自动生成）
```
`improvement_index.json` 的 brief 字段：
- `id`、`title`、`file`
- `status`：见 §5.2
- `priority`：见 §5.2
- `in_architecture`：是否已写进某 `architecture` 计划（如 `004`）
- `implemented_in`：被哪个 `architecture` 版本实施（如 `v0.4`）；未实施为空

### 5.2 标度（Q23 确认）
- **priority**：
  - 1 Very Low　2 Low　3 Median　4 High　5 Very High
- **status**：
  - 1 Drafting（起草，未进计划）
  - 2 Recorded In Architect（已写进某 architecture 计划）
  - 3 Implemented（已实施，**该 md 冻结**，仅可 correction note）

### 5.3 规则
- **只增不减**：新改进追加新文件；不删除。
- **可修改但每次留痕**：未实施（status<3）的 improvement md 可改；任何修改必须追加一条 `history` 事件留痕（如 `plan_modified` 指向该 `improvements/NNN.md`）。
- **implemented 后冻结**：status=3 的 md 不可再改内容，仅允许追加 correction note（同样留痕）。
- **TOC 派生**：`improvement_TOC.md` 从 `improvement_index.json` 渲染，最近 N 条出链防膨胀；关键信息（status/priority/in_architecture）同步到 TOC。

### 5.4 脚本扩展
- `append --kind improvement --body <file>`：创建 `improvements/<zeroed_id>.md` + 更新 `improvement_index.json` + 刷新 TOC。
- `gen-toc --kind improvement`：重建 `improvement_TOC.md`。
- audit 增加 `improvements` 一致性校验（文件夹 vs index）。

## 7. 采用方项目结构（install 后）

```
<project>/
  .plan-standard/            # 已安装的框架（或引用统一本地安装目录）
  standard_version           # 锁文件：standard_version=v0.4, pinned=...
  .codebuddy/
    settings.json            # hook 指向 .plan-standard/scripts/turn_gate.py（每项目一份）
  history/  questions/  issues/  improvements/
  architecture/              # 项目自身领域设计版本（轴 B）
  architecture_index.json    # 项目领域版本（轴 B），与框架版本轴 A 区分
```

### 7.1 `standard_version` 锁文件
声明采用方所用框架版本（轴 A），由 `install/update-standard` 维护，提交进采用方 git。

### 7.2 hook 每项目一份
采用方项目的 hook 由 `install-standard` 写进**该项目**的 `.codebuddy/settings.json`（不是全局共享一份）。hook 指向**该项目本地已安装的框架路径**（`.plan-standard/scripts/turn_gate.py`），使项目自包含、不依赖框架 repo 是否检出。
> 实现细节（拷贝到项目内 `.plan-standard/` vs 引用统一本地安装目录）在 §8 执行时定稿；不影响本计划启动。
