# 采纳方实测暴露的三处框架缺口修复 — architecture 006 / 目标 v0.6

> **状态：待执行（planned）。** 本计划吸收 `improvements/001.md`、`improvements/002.md`、`improvements/003.md` 三点，统一在下一框架版本（v0.6）落地。三项均来自采纳方项目（euston_wiki）实测暴露的缺口，由本框架仓库 dogfooding 吸收。聚合来源见对应 improvement 文件。本文件即 v0.6 权威计划；`architecture_index.json` 的 `latest_version` 升 6，`implemented_version` 待执行后置 6。

## 0. 背景与三项缺口

- **IMP-001（结构守卫）**：agent 在 euston_wiki 编辑 `architecture/002.md` 时连续犯两处结构质量问题——插入不编号的浮动小节打断 `§0–§N` 序列；加「文档结构自指」式元注释复述已成立事实。根因是框架只强制「改了留痕」，不约束「改得好不好」。
- **IMP-002（发布链）**：euston_wiki 执行 architecture/002 时 agent 只做本地改动 + history 留痕，未触发任何 git 动作，直到用户显式要求才发布。用户最终要求：implement 场景下 `commit → push → tag` 必须强制、紧跟、连做，tag 版本号 = architecture 版本号。
- **IMP-003（版本可追溯）**：`history/NNN.json` 与 `history_index.json` 的 brief 均不记录该条记录基于哪个 `standard_version` 产生；根目录 `standard_version` 文件只是「当前锁」，不等于「每条历史的产生版本」，升级后历史失去版本上下文。

## 1. IMP-001 — 编辑受管架构文档的结构一致性 / 反冗余守卫

### 1.1 决策

在 `references/workflow.md` 新增「编辑受管文件」守卫节，沉淀 4 条硬规则；并新增可选 lint 脚本 `scripts/structure_lint.py`，由 `turn_gate.py record` 或 `append_history.py` 在写盘 `architecture/*.md` 时调用，作机械兜底。

### 1.2 守卫规则（写入 workflow.md）

1. **结构连贯硬约束**：编辑 `architecture/*.md` 时章节编号 / 层级必须保持连贯；**禁止插入不编号的浮动小节**打断既有 `§0–§N` 序列；新增顶层小节必须编号并入序列。
2. **禁冗余元注释**：禁止「文档结构自指」式表述（如「本节属于本版本 / 不属于 §X / 已不含于某处」）。版本归属由文档整体决定，章节内容本身已说明，复述即废话。
3. **意图翻译步骤**：编辑前先把用户字面指令翻译为「意图」，再选**最贴合文档既有结构**的落点（通常并入已有相关章节），而非新建平行区块。
4. **编辑后结构自检清单**：编辑受管文档后须自检 ① 编号连续；② 无与既有内容重复的陈述；③ 无自指元注释；④ 改动确实落在意图所指位置。通过后再声明完成。

### 1.3 可选 lint 脚本

`scripts/structure_lint.py <plan>`：对 `architecture/*.md` 校验 ① 顶层标题序号是否从 0 连续、是否存在未编号浮动小节；② 是否出现 `本版本|后续|不属于|已不含|§X 已` 等自指措辞。命中则返回非零退出码，供 `turn_gate` / `append` 警告或阻断。

## 2. IMP-002 — set-implemented 发布链（commit → push → tag）

### 2.1 决策

将发布动作从「仅 commit 或交用户触发」改为**强制连做链**。修改 `scripts/append_history.py` 的 `cmd_set_implemented`：在翻转 `implemented_version`、刷新 TOC 之后，追加 git 动作链。

### 2.2 实现

- 解析 `--version N` → tag 名 `v{N}`；title 取 `architecture_index.json` 中对应 `version` 的 `title`。
- 连做（任一失败则整体失败并提示，不部分提交）：
  ```bash
  git add -A
  git commit -m "implement architecture/NNN: <title>"
  git push
  git tag v{NNN}
  git push --tags
  ```
- 框架自举：本仓库自身 `set-implemented` 同样适用（dogfooding），architecture 被置为 implemented 时即打 `v{NNN}` 并推送。

### 2.3 范围边界

- 唯一触发条件 = implement 一个 architecture（执行 plan 或 `set-implemented` 翻转 `implemented_version`）；bookkeeping（改进提案 / correction / Q&A）agent 不得 commit / push / 打 tag。
- tag 版本号严格等于被实现的 architecture 版本号，不得延迟或留给用户手动触发。

## 3. IMP-003 — history 携带 standard_version（版本可追溯）

### 3.1 决策

在 `history/NNN.json` 事件 schema 新增结构化字段 `standard_version`；`append_history.py` 落盘时从项目根 `standard_version` 文件读取当前版本并写入（快照语义，写入后不随后续升级改变）。

### 3.2 实现

- `append_history.py`：记录前读取 `standard_version` 文件（`standard_version=<ver>` 行），注入事件体 `standard_version` 字段；生成 `history_index.json` brief 时一并带出。
- `references/workflow.md` 的「记录规范」节说明：该字段由脚本自动注入、禁止手填、代表「本事件产生时所依据的框架版本」。
- `references/history_schema.md` 字段表新增 `standard_version`（string，快照）。

### 3.3 语义

- 升级框架（install-standard 写入新版本）后，新事件自然带新版本号；旧事件保留旧版本号，逐条可追溯。
- 不影响 `standard_version` 文件本身的「当前锁」语义（前者=逐条快照，后者=当前钉版）。

### 执行偏差（须记录）

- **tag 格式 `v0.6` 而非计划字面 `v{NNN}`→`v6`**：architecture/006 §2.2 字面写 `git tag v{NNN}`（version=6 应得 `v6`）。但本仓库既有 tag 为 `v0.3/v0.4/v0.5`，且 `check-standard`（`standard_ops.py` 的 `parse_version` 仅匹配 `vX.Y`）只认 `vX.Y` 格式；若打 `v6`，`check-standard` 会持续误报「落后」。为框架自举一致性，发布链采用 `v0.{version}`（即 `v0.6`）。这是与计划字面指令的有意偏差，理由是不破坏版本上报工具。
