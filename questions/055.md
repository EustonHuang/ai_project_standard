## Q55 — 2026-10-24

**问题（对 Q53/Q54 的勘误与结论）：**
CodeBuddy 存储会不会被清理？我明明看到 `history/2be0b7e7…/899a2f47…/messages` 是空文件夹。请把结论写进 questions。

**答案（实测修正后的结论）：**

### 一、勘误：Q53/Q54 的「0 个空文件夹」结论有误

上一轮扫描用了 `-maxdepth 2`，只检查了 **session 文件夹本身**是否为空，没深入其内部的 `messages/` 子目录——漏掉了「壳内有空目录」的情况。用户实测抓到反例：
`history/2be0b7e7c1ba3b5ede1d8f759daef946/899a2f47f7af44fc8880eb7febea4a51/messages` 为空。

### 二、修正后的正确口径与数据

正确检查 = session 的 `messages/` 目录为空 **或** `index.json` 消息数为 0。全量扫描结果：

| 指标 | 值 |
|---|---|
| session 总数（history/） | 236 |
| **空壳**（messages 空或 index 0 条） | **75** |
| 有内容 | 161（消息数 2 ~ 2171） |

### 三、结论

1. **空壳 = 出生即空的弃用会话，不是清理的痕迹。** CodeBuddy 在会话被打开时就建好骨架（空 `index.json`=`{"messages":[]}` + 空 `messages/`）；没发过消息（开了新聊天就切走、发送失败）就永远留下空壳。实例 `899a2f47…`：创建于 10-17 10:31，零条消息，此后从未改动——**它至今原样存在，恰恰反证 history 没有激进清理器**（否则空壳早被扫掉）。
2. **目前所有证据指向「只增不删」的累积行为**：236 个文件夹（含 75 个空壳、最早至 10-17）全部健在，没有发现任何消息曾被删除的痕迹。
3. **保留策略依然无官方承诺**：文档未记载该目录的保留/清理规则；IDE 升级、UI 删除会话、磁盘清理等仍可能影响它。**归档别依赖它**：要长期保留的会话自己拷出来，或按 Q52 方案 B 把要紧内容接进自有 trace。
4. **assets 与消息同生命周期**，同样无保留承诺（本 session 的截图实测仍在）。
5. 方法论教训：**下「不存在/为零」的结论前，扫描深度必须覆盖到最深层级**——浅层扫描会漏掉子目录层面的真相。

### 四、给读者的速判口诀

看到空 session 文件夹 → 先分辨在哪一层：`plan-task/` 下的空壳=没用过任务功能（239/256 空）；`history/` 下的空壳=打开过但零消息的弃用会话（75/236）。两者都不是「被清理」的证据。
