## Q32 — 2026-10-15
**问题：** ① 你为什么要设计 `implements_to`？我哪里提示你要设计这个玩意？我只是告诉你 custom-feature 的路径以及它里面会有哪些东西，没说 `implements_to`。② `implements_to` 是什么意思？我只是想对某些 feature 做**有序记录**而已，没说这个 feature 最终要不要 implement，它甚至不用 implement、就是记录。③ 假如你理解了我说的，当初你设计 `implements_to` 的初衷是什么？

**答案：**

### 1. 你确实没提示要设计 `implements_to`

你上一轮给的蓝图只规定了四件事：
- 目录格式 `custom/{feature}/{number}_{topic}.md` + 可选的 `{number}_{topic}/` 辅助目录；
- 一个 `register-custom-feature` 注册机制（写入 `custom_categories.json`）；
- 受管文件必须含 `custom/` 且其改动留痕；
- 任一 feature 更新要同步 `{feature}_TOC.md` 与 `{feature}_index.json`。

通篇没有"implement"这个词、没有"审批门禁"概念、更没有"实施产物路径"。所以 `implements_to` **不是你要求的，是我自己加进 `custom_categories.json` 的**。

### 2. `implements_to` 当初的初衷（诚实溯源）

来源是**更早一轮**你说过的一句话：「AI 做的 topic plan 必须经过我审核才能 implement」。

我当时把这句话当成需要"机器强制执行"的硬规则，于是设计了一套通用审批门禁：
- 状态机（`draft → review → approved → implemented`）；
- 一个字段告诉门禁"这个 feature 的实施产物落在哪"——就是 `implements_to`；
- PreToolUse 在写命中 `implements_to` 的路径前，检查该 feature 是否有 `approved` 记录。

也就是说，`implements_to` 的初衷是：**给"批准后才许实施"这个门禁提供"实施产物在哪"的映射**。它是为了那条针对 topic_plan 的具体要求而生的。

### 3. 为什么这是过度设计 / 错读

我犯的错误是把"topic_plan 这一个 feature 需要审批"**泛化成了通用 schema 的字段**：
- 你的通用 custom-feature 机制本质是**有序记录**（按序号归档、TOC/index 同步、留痕），很多 feature 根本不 implement、纯记录；
- 给每个 feature 都塞一个 `implements_to`（以及它隐含的"实施产物 + 审批门禁"语义），等于让所有 feature 都背上它未必需要的概念；
- 你现在的澄清正好印证了这点：custom-feature 就是记录，不一定要 implement。

所以 `implements_to` 不该出现在**通用** `custom_categories.json` 里。它源于一个具体 feature 的具体要求，被我错误地提升成了通用字段。

### 4. 结论与建议

- `implements_to` 应从 generic schema 移除；通用 `custom_categories.json` 每项只需 `name` + 可选 `description`（即"有序记录"所需的最小信息）。
- 如果将来某个**具体** feature（比如 topic_plan）真的要"人批后才许产出某类文件"，那是那个 feature 自己的特殊规则，不该是每个 custom feature 都背的字段——届时再单独处理，而不是现在写进通用 schema（YAGNI，且你已明确通用机制只是记录）。

注：这与 Q30 一致（不为假想/过度的通用性加配置项）；差别是 Q30 把 `implements_to` 当成"自动派生门禁的最小必要字段"保留，现在你澄清通用机制只是记录后，它连"最小必要"都不算了，应彻底移出。
