## Q38 — 2026-10-23

**问题：**
记录 `history/NNN.json` 时，每个字段是怎么填的？`schema_version` 为什么是 `2.0`、`event_type` 为什么是 `plan_modified`——它们从哪来、应取什么值？我想知道每个字段到底怎么记。另外，记录通常靠什么触发？靠 skill、靠 hook，还是别的？请记录到 questions。

**答案：**

### 一、每个字段怎么记（`history/{zeroed_id}.json`）

以 `history/085.json` 为样板，逐字段说明「来源 / 取值 / 谁填」。`append_history.py` 的 `cmd_append_history`（L622–691）是实际落盘的入口，下表标注哪些由脚本自动注入、哪些由 agent（我）手工写。

| 字段 | 来源 / 取值规则 | 谁填 |
|------|----------------|------|
| `schema_version` | 脚本常量 `EVENT_SCHEMA_VERSION = "2.0"`（`append_history.py` L56）；`event.setdefault("schema_version", EVENT_SCHEMA_VERSION)`（L631）。新事件永远是 `"2.0"`；若你手填了就保留你的值。bump 策略见 `history_schema.md` §「schema_version bump 策略（Q18）」：删/重命名字段=MAJOR，仅加可选字段=MINOR。 | 脚本自动（或沿用你给的） |
| `event_id` | 脚本从 `history_index.json.max_id + 1` 算出（L627），同时作为文件名 `history/{zeroed_id}.json`；`event["event_id"] = next_id`（L632）。用完不回收。 | 脚本自动 |
| `event_type` | agent 从 `record_types.md` §1 枚举里选：`history_initialized` / `plan_created` / `plan_modified` / `plan_accepted` / `plan_rejected` / `plan_reopened` / `correction` / `comment_added` / `qna_recorded`。085 选 `plan_modified` 因为它是在用户指令下 implement architecture 008（AI 改写/扩展 plan）。 | agent 手工 |
| `actor.type` | 枚举 `ai` / `human`（`record_types.md` §3）。AI 按 prompt 驱动=`ai`；事后检测到的手动编辑=`human`，此时 `source.user_prompt="(manual edit - no prompt available)"`。 | agent 手工 |
| `actor.identity` | 自由串。AI 事件写 `"CodeBuddy agent"`。 | agent 手工 |
| `actor.detail` | 自由叙述，描述本次 actor 做了什么（085 写的是 implement 008 的概括）。 | agent 手工 |
| `source.user_prompt` | 触发本次改动的**用户原文**（verbatim，`workflow.md` §2）。085 = `"现在请implement architecture 008"`。 | agent 手工 |
| `source.prompt_language` | `"zh"` / `"en"` 等，按 prompt 实际语言填。 | agent 手工 |
| `source.model` | **平台可信信号**：`resolve_source_model`（L319）优先取 `env CODEBUDDY_MODEL`；否则置 `"unknown"`。agent **禁止自报 `"Hy3"`**。085 因 env 缺失 → `"unknown"`。 | 脚本自动 + agent 兜底 |
| `source.model_confidence` | `"confirmed"`（平台给出）/ `"inferred"`（--model 传入）/ `"unknown"`（无信号）。085 = `"unknown"`。 | 脚本自动 |
| `source.tool` | 自由串，描述用什么工具做的。085 = `"CodeBuddy (replace_in_file + execute_command)"`。 | agent 手工（可选） |
| `operation.target_files` | 本次改动涉及的受管文件（相对路径）列表，须覆盖本轮所有改动，否则 Stop hook 拦。 | agent 手工 |
| `operation.change_summary` | 一句话概括改了什么（索引 brief 直接复用此串）。 | agent 手工 |
| `operation.sections_affected` | 受影响章节/文件清单（可以是 §编号或路径）。 | agent 手工 |
| `operation.qna`（仅 `qna_recorded`） | `{ question_ref, question, answer_summary, answer_location }`（`workflow.md` §7）。085 不是 qna，故无此键。 | agent 手工 |
| `correction` | 通常 `null`；当 `event_type=="correction"` 时填 `{ corrects_event_id, reason, detail }`（`history_schema.md` §4）。 | agent 手工 |
| `comments` | 自由文本，记不确定项。085 记了 model 取 unknown 的原因 + set-implemented 发布纪律。`source.model` 取不到时，脚本也会把说明追加进 `comments`。 | agent 手工 + 脚本补充 |
| `recorded_by` | `"ai"` / `"human"`，通常等于 `actor.type`（`record_types.md` §6）。 | agent 手工 |
| `recorded_at` | 脚本 `event.setdefault("recorded_at", now_iso())`（L633）；`now_iso()` 取本地时区 ISO-8601（L75–76）。**没有 `timestamp` 字段**（architecture 001 已删）。 | 脚本自动 |
| `standard_version` | 脚本 `read_standard_version(plan)`（L637）读项目锁文件 `standard_version` 的 `standard_version=<ver>` 一行 → `"v0.8"`。是一次**快照**，写后永不变；**禁止手填**（IMP-003 / architecture 006）。同一值镜像进 `history_index.json` brief。 | 脚本自动 |
| `plan_state_snapshot` | 脚本 `attach_snapshot`（L282）自动附最新 `architecture/<latest>.md` 的快照：`plan_md_sha256`、`plan_md_line_count`、`source_doc`（如 `"architecture/008.md"`）。若事件里已带则保留（L284 `if "plan_state_snapshot" in event: return`）。 | 脚本自动 |

> 易混点：`schema_version` 是**事件级**（每个文件内），不是文件级；`standard_version` 是**框架版本快照**（来自锁文件），两者完全不同轴。

### 二、记录靠什么触发

**不是靠一个叫「record」的 skill。** 机制分三层：

1. **落盘工具 = `append_history.py` 脚本（框架引擎），由 agent 手动调用。**
   - 历史：`python scripts/append_history.py append --plan . --event event.json`（或 `--event -` 读 stdin）。
   - 问题/改进：走 `--kind questions` / `--kind improvement`（写正文 + 更新对应 index + 自动生成 TOC）。
   - 脚本负责分配 `event_id` / 盖 `recorded_at` / 解析 `source.model` / 附 `plan_state_snapshot` / 注入 `standard_version` / 写文件 + 更新 `history_index.json` + 重生 `history_TOC.md`，并在锁 + 索引哈希守卫下提交（防 stale-read / collision / lock-timeout）。

2. **机械兜底 = CodeBuddy Hooks（`turn_gate.py`），本仓 `.codebuddy/settings.json` 已接好四条：**
   - `UserPromptSubmit → begin`：记 `baseline_max_id`。
   - `PreToolUse → prewrite`（D2）：写受管文件前硬拦截，目标必须 ∈ 受管白名单或命中 `.turngateignore`，否则拒写（exit 1）。
   - `PostToolUse → record`：记账本轮编辑工具碰过的每个 in-plan 文件。
   - `Stop → end`：**硬门**。若本轮改了 plan 文件，必须有 `event_id > baseline` 且其 `operation.target_files` 覆盖这些文件的事件，否则 `exit 2` 强制回头补记。这就是「任何改动都要进 history」的强制保证。

3. **加载保证 = always-applied workspace rule（README MANDATORY 节）：** 每会话开始注入「任何改动必须留痕」，并规定事件类型映射；这是纪律层，hook 是机械背书。

**结论**：触发 = agent 的纪律/你显式指令「记到 questions」+ 手动跑脚本；**hook（turn_gate）是强制兜底而非触发器本身**；框架本体是「项目规范」不是 CodeBuddy skill，但随附 `install-standard` / `update-standard` / `check-standard` 三个 skill 用于「采纳/升级/查看版本」。

### 三、questions 的双录纪律

你这次说「记到 questions」触发的是**双录**：
1. `append --kind questions --body q.md --question-ref Q38 --question "..." --answer-summary "..."` → 写 `questions/038.md` + 更新 `questions_index.json` + 重生 `questions_TOC.md`；
2. 再手跑一次 `append --event` 追加一条 `event_type="qna_recorded"` 的 history 事件（其 `operation.target_files` 含 `questions/038.md`，并带 `operation.qna`）。
缺任一步 Stop hook 都会判 uncovered 并 exit 2，故漏记会被机器拦下。
