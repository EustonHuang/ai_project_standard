## Q33 — 2026-10-15
**问题：** architecture/008.md 里的「3. D3 — 记录规范」这个记录规范，是关于什么的记录规范？

**答案（依据 architecture/008.md §3，及 D1/D2/D4 的分工）：**

### 1. 它管的是「custom feature 内部每一条记录」的规范

「记录」指的是 `custom/<feature>/` 目录下的**一条具体条目**——一个 markdown 文件，例如 `custom/topic_plan/001-spark-helloworld.md`。`topic_plan` 是一个 feature；`001-spark-helloworld.md` 是它里面的**一条记录**。

D3 与另外三项的分工要分清：

| 章节 | 管什么 |
|---|---|
| D1 注册制 | 有没有这个 feature（注册清单 `custom_categories.json`） |
| D2 目录格式 | feature 文件夹里文件/目录怎么**命名排布**（序号开头 + 同名辅助目录） |
| **D3 记录规范** | **每条记录自己长什么样、怎么改**（本问答主题） |
| D4 同步与留痕 | 改完怎么同步 index/TOC、怎么进 history |

所以 D3 不关心"有没有这个 feature""文件叫什么名""索引怎么生成"，它只关心**单条记录的内容结构与演进方式**。

### 2. D3 具体规定了两件事

**① 一条记录的结构（§3.1）**
- 一条记录 = 一个文件（不是"一个文件夹一条记录"，是扁平的一个 `.md`）。
- 元数据写在文件头 frontmatter：`revision` / `supersedes` / `change_summary` / `aux_files`。正文在下面，**永不就地改**。
- 该 feature 的 `<feature>_index.json` 的 brief 会镜像这些 frontmatter 字段（`num`/`topic`/`revision`/`supersedes`/`change_summary`/`aux_files`/`file`），让读者不点开文件也能概览。

**② 记录的修订方式（§3.2）**
- 要改一条记录，**不就地改**，而是**追加一个新序号的文件**：`revision+1`、`supersedes` 指向上一版、`change_summary` 逐条写明改了什么。
- 旧记录正文就此冻结（append-only）。这样"每次改了什么"天然可查，与 `questions/` 的 append-only 同源。

### 3. 一句话总结

D3 是 custom feature 内部"**有序记录**"的规范：它规定每一条记录是一个带 frontmatter 的扁平 md 文件，且修改采取追加新版本、不就地改的 append-only 方式。它服务的是你那句"对某些 feature 做**有序记录**"——只管记录本身怎么写、怎么演进，不管注册、命名排布或同步。
