## Q13 — 2026-10-03
**问题：** `questions_TOC.md` 的设计是不是多余？因为 `questions_index.json` 里已有相应内容，唯一美中不足的是 JSON 不能给链接、用户想直接点链接跳转。总而言之，想要的是"索引 + 具体文件"两部分，而现在新增一个问题要改三个地方——这真的比只有一个 `questions.json` 更有优势吗？存疑。有没有办法尽量拆成两部分（索引 + 内容），且索引不能太长——因为索引本质上还是 json append，我们这么做的初心是解决 json 越加越长；假如索引太长不好维护，就又回到了当初的坑。

**答案（讨论，未执行）：**

**1. questions_TOC.md：作为"需维护的第三处"是多余的；应降级为按需生成的派生物。**
- 它唯一不可替代的价值是**可点击链接**（JSON 给不了）。这个价值真实存在，但不该靠"每次手工维护第三处"来换。
- 解法：保留为**脚本按需生成**（如 `gen-toc` 命令），不纳入日常维护。日常只需两处：内容 + 索引。

**2. "三个地方"其实已经可以收敛到一处人工维护。**
`append --plan DIR --kind questions --body q.md ...` 一步内完成：写入 `questions/011.md` + 更新 `questions_index.json` + 重生成 TOC。也就是说人或 agent **只写内容**，索引与 TOC 由脚本派生。若按上面把 TOC 改为按需生成，则日常只有"内容 + 索引"两处，且索引由脚本自动更新。

**3. 是否真的优于单个 questions.json？是，但理由要说准。**
真正的收益不是"文件变多了"，而是：
- **append 成本恒定**：写新文件，不必读取/重写整份历史（这正是当初的坑）；
- **原子写**：不再"读整个大文件→重写"，消除大文件重写损坏/竞态风险；
- **并发 / Git / diff 友好**：每问答一文件，提交清晰、无大 JSON 合并冲突；
- **按需读**：只读需要的那一个文件，不必载入全量。

**4. 索引会不会又变回"当初的坑"？关键在于区分"真相源"与"派生缓存"。**
- **append 时模型不需要读索引**：脚本在磁盘上读索引、算 `max_id`、写新文件、更新索引——上下文成本恒定。所以**最核心的那条坑已经彻底解决**，不会回来。
- 索引变大只影响"总览/查找"（`show`）。缓解手段：
  - briefs 每行极紧凑（仅 event_id/type/time/摘要），比完整 event JSON 小一个数量级，增长慢得多；
  - `show` 默认只读尾部 N 条（`--last N`），不全量载入；
  - 真到很大时可**按区间分片**，或直接 `rebuild-index` 从内容文件重算。
- **根本区别**：当初的单文件 `questions.json` 既是真相源又必须整体读写，没有逃生舱；现在**内容文件才是真相源，索引是派生、可重建的缓存**。最坏情况也只是重建一个缓存，不会丢数据——所以"索引太长不好维护"不致命。

**结论：**
保留"索引 + 内容"两部分；`questions_TOC.md` 改为按需生成（不再手工维护第三处）；索引保持可重建，并为 `show` 加尾部窗口、必要时支持分片以防膨胀。
