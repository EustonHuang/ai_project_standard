## Q27 — 2026-10-15
**问题：** architecture/008.md §1.2 表里有一项 `record_file`（⬜ 选填）——“记录正文文件名，默认 `record.md`（euston_wiki 可用 `plan.md`）”。这一项的意义是什么？要求回答时不改任何设计，并给出 3 个例子说明。

**答案：**

### 一句话

`record_file` 是**「一条记录文件夹里，那份给人看的正文档案叫什么名字」的命名旋钮**，除此之外不承载任何语义。

### 为什么需要它

008 的 D2 规定一条记录 = 一个文件夹，文件夹里放两类东西：

- `record.json`：结构化元数据（id / subject / revision / supersedes / status / change_summary / approved_by …），给**引擎**读；
- `<record_file>`：**正文**，即那份真正给人看的 plan/RFC/提案文本，给人读。

引擎要做三件事都必须知道正文的确切文件名：

1. **TOC 链接**：`<category>_TOC.md` 的行要链到可读正文，而不是链到机器读的 `record.json`—— `- [004 · … · approved](topic_plan/004/plan.md)`；
2. **`custom append --body X`**：把外部写好的正文按这个名字落进记录目录；
3. **`audit` 校验**：确认每条记录存在着一个正文文件（缺了就是坏记录）。

因为框架是元规范、不可能知道每个领域的叫法，所以把它做成**声明项**（在 `custom_categories.json` 里写明），而不是像五大内置栏目那样在 `append_history.py` 里硬编码——这与 D1 的总体取向一致（Q11 教训：常量要变成项目级可声明的配置）。

### 它**不是**什么（边界）

- 不是「可以有多个正文」：一个记录只有一个正文文件，`record_file` 是单数；多份材料一律进 `assets/`，或拆成另一个栏目。
- 不影响修订/审批语义：`revision` / `supersedes` / `status` 全部写在 `record.json` 里；正文文件名改了不会自动产生第二个版本（版本只由 `revision`/`supersedes` 决定）。
- 不影响 id 与目录布局：路径仍是 `<dir>/<id>/<record_file>`，`<id>` 依旧由索引 `max_id+1` 分配。

### 3 个例子

**例 1｜euston_wiki 的 `topic_plan`（字段存在的典型理由）**

```json
{ "name": "topic_plan", "dir": "topic_plan", "record_file": "plan.md" }
```

产出：

```
topic_plan/004/plan.md        ← 正文：topic「ClickHouse 备份」的编写计划，给人读
topic_plan/004/record.json    ← status=approved / revision=2 / supersedes=3
topic_plan_TOC.md             → - [004 · 23-clickhouse-backup · v2 · approved](topic_plan/004/plan.md) — ①…
```

意义：这个领域的语言就是「plan」，让文件路径、TOC 链接、编辑器里的文件名都叫 `plan.md`，而不是所有人都得适应框架造的词 `record.md`。

**例 2｜某项目的 `spec_change` 栏目（团队术语延续）**

```json
{ "name": "spec_change", "record_file": "RFC.md" }
```

产出：`spec_change/007/RFC.md`。团队原本就把这类文档叫 RFC，改名成本高且易混淆（旧 RFC 编号要与新 id 对照时多一层心智负担）；声明 `record_file` 后，**引入新栏目不必重命名既有概念**，TOC 仍自动链接到 `spec_change/007/RFC.md`。

**例 3｜不声明（默认 `record.md`）**

```json
{ "name": "meeting_decision" }
```

产出：`meeting_decision/003/record.md`。此时该字段根本不出现在声明里——它是选填项，**不声明 = 用默认值**，行为与声明 `"record_file": "record.md"` 完全一致。例子说明：字段只是逃生口，不是每个栏目都要填。

### 诚实的补充判断

这是一个**纯「化妆」性质的旋钮**：给它带来的全部收益是「文件名/链接名贴合项目用词」，没有任何结构性收益。反过来说它的成本也很低（一个可选字符串，引擎读一次）。因此它属于**审阅时可以直接砍掉**的项——若认为每个项目的用词差异不值得一个配置项，就把 §1.2 的 `record_file` 行删掉、引擎固定用 `record.md`，D1/D2/D3/D4 与 §6 网关全都不受影响。按用户本次要求，未做任何改动。
