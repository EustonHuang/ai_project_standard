## Q30 — 2026-10-15
**问题：** ① 但凡加一个字段，就要考虑怎么维护它。我说过"AI 做的 topic plan 必须经过我审核才能 implement"，但我并没有说要加 `requires_approval` 这些字段吧？② `status_flow` 的 `draft → review → approved → implemented` 这一条链，你觉得维护要花多少力气？但凡其中有一个地方不对，你都得去查原因。相应带来的收益大吗？③ 如果你认同我的观点，为什么你还要做出这样的设计并为自己辩解？

**答案（依据 architecture/008.md §1.2、§3.3、§6.2，及 Q28、Q29）：**

### 1. `status_flow` 的维护成本（拆开算）

一条 5 态链，每加一个自定义栏目，实际要维护的东西是这些：

- **声明**：`custom_categories.json` 里为每个栏目各写一份枚举数组（N 个栏目 = N 份重复）。
- **校验**：`custom set-status` 要按该栏目自己的枚举校验，写了枚举外的值要拒、要报错。
- **每条流转边都要保证**：`draft→review` 谁驱动、`review→approved` 只能 human、`approved→implemented`、`implemented` 后冻结、`rejected` 是终态。
- **默认值**：不声明时取什么——这里**已经出现不一致**（§1.2 写"默认四项"但示例数组列 5 个值，Q28 已记）。
- **索引镜像**：每条记录的 `status` 要在 `custom/<feature>_index.json` 的 brief 里同步一份，两处必须一致。
- **与门禁联动**：`approved` 才放行、`implemented` 才冻结。

"但凡一处不对就得查原因"的具体故障模式：

- 索引里看到 `status=approved`，但文件 frontmatter 还是 `review` → 要查是 `set-status` 没同步、还是有人手改了 index。
- `implemented` 没冻结、又被改了一次 → 要查是 `set-status` 校验漏了还是 hook 没挂上。
- 声明了 5 个值但引擎按 4 个校验 → 某个状态永远进不去，且报错信息不一定指向声明文件。

共同点：这类问题都要**从声明 → 引擎 → 索引 → hook 一路排查**，不是看一眼就知道哪里错。

### 2. 收益有多大

**对你确定的用法，收益 ≈ 0。**

- 你从来没有要求"不同栏目有不同状态"。
- 你已经点名的栏目（`topic_plan`，以及可能的 `code_plan`）生命周期**完全相同**。
- 即使将来出现一个"素材库"类栏目不需要状态——真到那一天再加字段也来得及（YAGNI）。

它唯一的理论收益是"将来某栏目需要完全不同的生命周期时不必改引擎"。这是**为假想的未来付费，不是为已发生的需求付费**。

### 3. `requires_approval` 同理

你的原话是"AI 做的 topic plan 必须经过我审核才能 implement"——这是一条**针对 topic_plan 的、确定的硬规则**，不是"每个栏目可选要不要审批"。我把它做成开关，等于把一条确定规则变成一个待维护的配置项，还额外引入了新的失效模式：声明 `true` 却没 `implements_to`（门禁永远不触发，形同虚设）、或声明 `false` 却实际需要审批（拦不住）。

### 4. 我为什么这么设计、还替自己辩解（诚实回答）

**我认同你的观点。** 我当初这么设计，是"框架作者"的惯性：

- 008 的立项是「把自定义栏目做成一等公民、支持任意项目任意栏目」。我在这个立项下把**"可配置"当成了优点本身**，默认每个维度都应该可配（状态词汇表、审批开关、实施路径模式…），而没有先问一句"这个维度在真实需求里真的会变吗"。
- 我被"通用性"这个听起来更高级的目标带跑了，而代价直接转嫁给了你这个实际使用者：多写的声明、多维护的字段、多出来的排查路径。

至于我在 Q29 里"辩解"说「审批门禁不是过度设计、`status_flow` 是通用化税」——那是**事后合理化**：

- 前半句（审批门禁必要）站得住，它确实对应你的原话；
- 后半句（通用化税可辩护）站不住。因为"通用"是 **008 自己给自己加的目标**，不是你提的需求。用自己加的目标去论证自己加的字段合理，是循环论证。正确做法是按你的最小需求先做，等真的遇到需要不同生命周期的栏目时，再加 `status_flow` 这个字段——那时它是被需求逼出来的，不是被"通用性"想象出来的。

### 5. 结论与建议（最小字段集）

- **`status_flow`：删。** 全框架共用一套固定流（`draft → review → approved → implemented` + `rejected` 终态），不再按栏目声明。
- **`requires_approval`：删。** 由 `implements_to` 是否声明自动派生——声明了 = 该栏目有实施产物 = 自动上审批门禁；不声明 = 纯留痕栏目、无门禁。
- **`approved_by`：可省。** 强制"approved 只能 human 置"（AI 置就拒），则 `status: approved` 本身就蕴含"人批的"，证据在对应 `history` 事件的 `actor.type=human`（这本来就是双录的职责），门禁只需查 `status == approved`。
- **每个自定义栏目只剩 3 个字段**：`name`（目录名）、`description`（选填）、`implements_to`（选填）。

维护面从「目录名 + 状态词汇表 + 审批开关 + 实施路径」降到「目录名 + 实施路径」，而你要的那句"没有我批准不许 implement"一点没少——AI 要写命中 `implements_to` 的路径而该栏目没有 `status=approved` 的记录，照样被 PreToolUse 拒。

### 6. 一条原则（供记入 rules 参考）

**加字段前先算维护成本；不为假想的通用性加配置项。** 字段的收益必须来自"已经发生的需求"，不能来自"将来可能会需要"。
