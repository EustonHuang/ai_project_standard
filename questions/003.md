## Q3 — 2026-10-03
**问题：** 去掉 `timestamp` 会改变 schema → `schema_version` 必然要变。若改变后，怎么实现 history.json 的只增不改？因为似乎要再加一个 `{}` 表示 `schema_version=1.1`，JSON 会从 `{}` 变成 `[{},{}]`，这就破坏了只增不改。建议是什么、怎么改？

**答案（讨论，未实现）：**
- **澄清误解**：把"整份文件"当版本单位才会需要 `{} → [{},{}]` 这种重构；我们版本化的是 **event**，不是文件容器。文件形状（顶层 object + `events[]`）始终不变，无需重构，因此也不破坏只增不改。
- **真正冲突**：append-only 禁止编辑任何已有内容，但顶层写死的 `"schema_version":"1.0"` 在 `init` 时空文件阶段写好、事件已存在后**不能**再改为 `"1.1"`（否则等于编辑历史）。这才是核心矛盾。
- **建议 A（推荐）：per-event `schema_version`**。顶层 `schema_version` 退化为"文件初始化格式版本"、永不再改；每个事件自带 `"schema_version":"1.0"/"1.1"`，新事件写 `"1.1"` 且不带 `timestamp`。读者按每个 event 自己的版本解析。完全不重构文件，旧事件不动。
- **建议 B（最省事）：把 `timestamp` 当可选字段，根本不 bump**。读者对 `timestamp` 做"有则用之、无则忽略"的容错解析；顶层 `schema_version` 维持 `"1.0"`，新事件直接不写 `timestamp`。连元数据都不碰，最贴合只增不改。
- **建议 C：重定义顶层 `schema_version` 语义**为"容器格式版本"（顶层 object + `events[]` 形状），几乎不变；event 字段演进交给 per-event version（A）或可选字段（B）。
- **不推荐**：把整份 history.json 重构成 `[{},{}]`——破坏只增不改且没必要。
- **落地到"去掉 timestamp"**：用 B（可选字段、不 bump）最干净；若要显式版本用 A。两者都**不需要改 JSON 结构、不需要迁移旧事件**——旧事件 `timestamp` 原样保留，新事件不写即可。

**History：** `qna_recorded` 事件（见 `history.json`，`event_id` 对应本问答）。本事件本身已按用户①方向省略 `timestamp` 字段，作为实践验证。
