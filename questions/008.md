**答案（审阅 + 新的修改计划，未执行）：**

### 一、逐点审阅与改进建议
整体设计**稳健**，issues 兜底尤其出色。以下 A–I 为可改进处：

- **A 顺序权威问题（重要技术修正）**：按字典序，`"1000" < "999"`（首字符 `'1' < '9'`），所以 999→1000 跨宽度时排序会错乱。你的"补 0 重排为 4 位"能修，但更稳的做法是：**以文件内 `event_id` 整数为唯一权威序，文件名宽度仅美观**。这样即使宽度不一也不影响重建顺序；索引重建 + `audit` 再兜底。
- **B 索引位置需 per-plan**：index 应作为 `history/` 的**兄弟**（plan 文件夹内），而非塞进 `history/`，且**必须每个 plan 一份**——多 plan 不能共用全局 index（否则 max_id 串味）。本 demo 中 plan 文件夹恰为该 skill 文件夹，故落点一致。
- **C 简要信息零额外成本**：直接复用事件内已有字段 `operation.change_summary` 与 `actor.type` 进索引，**无需额外 AI 总结**（你担心的耗时不存在）。建议索引简要 = `{event_id, event_type, recorded_at, actor_type, change_summary, is_correction?, corrects_event_id?}`。
- **D 双向 desync 检测**：`audit` 既查"index 领先"（目标文件已存在），也查"index 落后"（history/ 实际文件数 > index max_id）；两者都走 issues。
- **E issue 编号也防碰撞**：用同一把锁或原子 `mkdir issues/{num}`；建议加 `issues_index.json`。
- **F 锁防死锁**：锁含 PID + 创建时间戳，超 TTL（如 30s）视为失效可抢占，避免崩溃进程永久持锁。
- **G 乐观锁澄清**：你描述的是"**互斥锁 + 版本守卫**"混合（更稳），并非纯乐观锁（无锁 CAS）。两者都安全，混合更稳，保留即可。
- **H issue 资产齐备**：`description.json` 同时存"意图内容"与"现有冲突文件副本"，便于根因定位与 `recover` 重放。
- **I correction 一致**：`history/{id}.json`（event_type=correction, `correction.corrects_event_id`）在索引简要标 `is_correction/corrects_event_id`，与你的设想一致。

### 二、新的修改计划（工具重写 + 一次性迁移）
**目标布局（每个 plan 文件夹）：**
```
<plan>/
  history/        001.json … NNN.json        # 每事件一文件
  questions/      001.md … MMM.md + index.md # 每问答一文件 + 人类 TOC
  issues/         001/{description.json, assets/100.json} …  # 故障留档
  history_index.json   # max_id + 每文件简要 + revision/version
  questions_index.json # 每问答简要
  history_meta.json    # plan 级元信息 + 可选总览
  questions_meta.json
  .lock                 # 提交锁（PID + TTL 防死锁）
```
**脚本命令（`append_history.py` 重写）：**
- `init --plan DIR [--meta ...]`：建目录 + 空索引 + meta。
- `append --plan DIR --event E.json [--kind history|questions]`：见下提交流程。
- `show --plan DIR`：仅读 `history_index.json` 打印简要（**不扫 history/**，落实第 3/4 点）。
- `audit --plan DIR`：校验 history/ 与 index 一致性（缺口/多余/碰撞），输出 desync 报告，可触发 issues。
- `rebuild-index --plan DIR`：从 `history/*.json` 重算索引（索引可重建，符合 Q5 思想）。
- `migrate --plan DIR --from history.json --from-q questions.md`：一次性旧数组/单文件 → 新布局（含旧 Q1–Q7 拆文件 + 重建索引）。
- `recover --issue 001`：根因修复后，把 `issues/001/assets` 内容正式写入（重放）。

**append 提交流程（互斥锁 + 版本守卫）：**
1. 读 `history_index.json` → 记 `revision`/version 哈希，取 `max_id`。
2. `next_id = max_id + 1`，文件名 `zeroed(next_id)+".json"`。
3. 在 `issues/<staging>/assets/` 或 `.tmp/` 写**意图内容**（event_id/recorded_at 等由脚本补）。
4. 获取锁（原子 `mkdir .lock`，写 PID+TTL）；锁被占 → 退避重试 ≤ N 次；超次 → 建 issue（lock-timeout）中止。
5. 持锁下重读 index：若 `revision` != 步骤1 记录值 → 陈旧读（他人已提交）→ 释放锁，建 issue（stale-read，含意图内容）中止。
6. 检查 `history/{next_id}.json` 是否已存在 → 碰撞 → 释放锁，建 issue（collision，含意图内容 + 现有文件副本）中止。
7. 全通过 → 落盘 `history/{next_id}.json`，更新 `history_index.json`（max_id、revision+1、追加简要），释放锁。

**结论：** 设计恰当，按 A–I 微调后即可作为 `plan.md` 修订版执行（你已说先不执行）。迁移为一次性；旧事件/问答迁成文件、不回改内容，符合只增不改。
