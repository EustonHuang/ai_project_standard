## Q7 — 2026-10-03
**问题（新想法，未执行）：** 将 `history.json` 和 `questions.md` 拆成「文件夹 + 文件」的形式：
- `history.json` → `history/{event_id}_{event_type}.json`（如 `history/1_history_initialized.json`）
- `questions.md` → `questions/{question_num}.md`（如 `questions/1.md`）
你觉得如何？（先不执行/不改 plan，先回答问题，再记入 questions.md 与 history.json）

**答案（讨论，未改动 skill/脚本/plan）：**
方向很好，且比 Q5 提的「数组 + 轻量索引」更彻底地从根上解决上下文成本问题。

**优点：**
1. **根治上下文成本（呼应 Q5/Q6）**：agent append 时只需 `ls history/` 取最大 `event_id`、写一个**新文件**，完全不需要读任何旧事件内容——单次动作上下文成本**恒定**，与历史长度无关；比读数组再 append 或读索引都干净。
2. **append-only 变文件系统原生**：写新文件即追加，旧文件天然不可变（要改历史须动另一个独立文件，git diff / 文件系统一眼可见）；比在单数组里压入语义更纯粹，无法方便误改历史。
3. **原子性更好**：数组 append 是「读全文件→重写全文件」，大文件重写有损坏/竞态风险；写单文件（tmp+rename）更简单安全。
4. **并发友好**：多 agent / 工具可同时写不同文件，不会像单 JSON 那样 read-modify-write 抢锁。
5. **Git / diff 友好**：每事件一文件，提交清晰、无大 JSON 合并冲突；跨事件 grep（ripgrep 扫目录）也容易。

**落地前必须定的点：**
1. **零填充 ID + 命名约定（最关键）**：目录按文件名排序，`1_` 会排在 `10_` 前（字典序陷阱），必须零填充 `01_…`/`10_…`（`%03d`），否则顺序错乱。
2. **下一个 event_id 怎么拿**：列目录取最大数字前缀即可，不读内容，很便宜，但约定要清晰。
3. **总览/摘要怎么办**：不再「一次 load 全量」；`show` 变「列目录 + 读各文件小字段」。agent 日常只读需要的那一个文件，仅要总览才扫全部；单文件小，即便上千也远轻于读巨数组。
4. **索引变可选**：可加 `history/_index.json`（最新 id / 最近几条摘要），但文件级隔离下索引是锦上添花而非必需——这正是优于 Q5 方案处。
5. **questions/ 同理但建议保留 TOC**：`questions/{n}.md` 解决单文件膨胀，却失去一页滚动浏览；建议加 `questions/index.md`（目录/摘要），agent 读单文件、人审阅看 index。
6. **工具重写 + 一次性迁移**：现有 `append_history.py`（数组形态）要改写单文件，`show`/`migrate` 也要改；现有 10 个事件迁成 10 个文件是一锤子买卖。
7. **文件名里 event_type 是否冗余**：`event_id` 已唯一，event_type 进文件名仅为可读性，可接受，但改名要注意一致性。
8. **meta / correction 引用**：`history_meta.json` 保留；correction 的 `corrects_event_id` → 对应 `history/{id}_*.json`，引用更直观。

**结论**：值得做；在最底层就把「可信性（append-only）」与「读取效率（按需单文件）」解耦，比数组+索引更优雅。落地前定好零填充命名、是否保留 TOC、脚本重写方案即可。属 schema/工具演进，应作为新 event 落到 `plan.md`（用户已说先不执行）——届时旧事件迁成文件、不回改内容，符合只增不改。
