## Q18 — 2026-10-04
**问题：** 执行前发现 history 记录两个质量问题：
1. `source.model` 永远是 "Hy3"，但用户某次提问实际用的是 Hy4 preview（疑似事件 #024）。怀疑 model 被 hard_code，未记录真实模型。
2. `schema_version` 在去掉 `timestamp` 字段前后都是 "1.0"；去掉 timestamp 是 schema 变更，为何没把版本号改掉？为什么不改？
并请就两点给出"为何发生 + 解决方案"，记录到 questions；设计解决方案时不得改动 history 下任何 xxx.json，若需纠正用"新建 + 纠正 note"；并核查 skill 是否提及该"不得就地改、用纠正 note"的规则，一并记录。

**答案（分析 + 解决方案）：**

### A. model 是否 hard_code？——是，但在 agent 层，不在脚本层
- 实证：在 `scripts/append_history.py` 全文搜索 "Hy3"/`"model"`/`model_confidence` → **0 命中**。脚本从不写 model；它只把事件 JSON 里 `source` 块原样落盘（`append` 仅 `setdefault` `schema_version`/`event_id`/`recorded_at`/`plan_state_snapshot`）。
- 真正的来源：每次 `append` 的事件 JSON 由 **agent 自己构造**，而 agent 在 `source.model` 里固定写 `"Hy3"`——那只是 agent 系统提示里声明的"自身模型身份"，并非"本次响应用户的真实模型"。
- 为什么不可靠：平台**没有**给 agent 任何"本轮用户选用了哪个模型"的信号（没有 env var、没有 hook 入参、没有工具返回值）。当用户在某轮切到 Hy4 preview，agent 仍按自身身份盖 "Hy3"。所以 `source.model` 是**自报、且未校验**的，等于被 agent 假设"hard_code"了。
- 能否从数据确认哪条是 Hy4？**不能**——因为该字段正是不可信的那条；history 里 26 条全部写 "Hy3"。按用户陈述，可疑轮次是 Q16 → 事件 #024，其 `source.model` 存档为 "Hy3"；若用户确在该轮用了 Hy4 preview，则该记录即失真，恰好印证 bug。

### B. schema_version 为何删 timestamp 后仍 1.0？——缺版本策略 + 常量冻结
- 实证：`scripts/append_history.py` 第 48 行 `EVENT_SCHEMA_VERSION = "1.0"` 是**写死的常量**；`append` 第 334 行 `event.setdefault("schema_version", EVENT_SCHEMA_VERSION)` 只在缺失时补，不覆盖；`migrate` 第 644 行同理。
- 删除 `timestamp` 是一项**真实的 schema 形态变更**（字段被去掉），但当时：
  1. 从未定义"字段增删→版本号必须 bump"的规则（architecture 001 §0 讨论过 schema 演进 vs 只增不改，但没落成可执行的 bump 策略）；
  2. 没人改 `EVENT_SCHEMA_VERSION` 这个常量；
  3. agent 仍往 JSON 里写 "1.0"（或依赖脚本默认），于是新事件继续被盖上 "1.0"。
- 为何"不改"：把"去 timestamp"当成"可选字段缺失、reader 容错即可"处理，没当成需要版本化的演进；属于**政策缺失 + 常量冻结 + 疏忽**，不是有意为之。

### 解决方案
**Q1（model 真实性）：**
- 让脚本成为唯一真相源，不再信任 agent 自报：`append_history.py` 解析 `source.model` 时优先取**平台提供的可信信号**（如 harness 注入的 env var `CODEBUDDY_MODEL` 或 hook 上下文里的 model 字段）；取到才写真实 id，`model_confidence="confirmed"`；取不到则写 `"unknown"` 并在 `comments` 注明，绝不许 agent 用自身身份偷偷填 "Hy3"。
- `SKILL.md`/`record_types.md` 明确：**`source.model` 必须来自平台信号，禁止 agent 猜测**；未知即 "unknown"。
- 历史数据不可回改（见下），改用 `comment_added` 标注：既有 `source.model="Hy3"` 为自报/假设，凡用户切换模型的轮次可能失真；新事件改用平台信号。

**Q2（schema_version 策略）：**
- 在 `SKILL.md`/`history_schema.md` 立规：`schema_version` = 事件形态版本；**任何形态变更必须 bump**，按 semver：新增可选字段→MINOR（1.0→1.1），删除/重命名/改必填→MAJOR（1.0→2.0）。删 `timestamp` 属删除 → 本应 MAJOR（如 "2.0"）。
- `EVENT_SCHEMA_VERSION` 作为唯一真相源；形态一变就改常量；`append` 照旧 `setdefault` 当前值即可。可选加"按版本校验形态"的轻量检查。
- 立即把常量升到 **"2.0"**（反映"无 timestamp"形态），使新事件正确版本化；在 `comment_added` 注明：事件 #1–#14 带 `timestamp`（形态 1.0），#15 起无 `timestamp`（本应 2.0 但当时未 bump，仍标 1.0）——旧事件不回改，演进 lineage 由该注释说明。
- 上述脚本/文档改动应补进 `architecture/003.md` 的 §8 delta（v3 执行时一并落地），且执行本身也按 §10.1 先追加 history 事件。

### skill 是否提及"不得就地改、用纠正 note"？——**已明确提及（多处）**
- `SKILL.md` 第 8–9 行："Existing records are never edited; errors are corrected by appending a new correction event."
- `SKILL.md` 第 66–67 行（Append-only 规则）："never edit an existing event file. Fix mistakes by appending a `correction` event referencing `corrects_event_id`."
- `references/record_types.md`：`correction` = "Correction of a prior event (**new file; never edits in place**)."
- `references/workflow.md` §1 事件发射表："Wrong/uncertain prior record found → `correction` (**new file, never an edit**)."
- `architecture/001.md` §4："数组内每个 event **不可改**；纠错 = 追加 `correction` event（引用 `corrects_event_id`），原 event 不动。"
结论：该原则是 skill 的一等公民，本 Q18 的解决方案（新建 `comment_added` 标注、不回改旧文件）正是依规行事。
