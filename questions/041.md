## Q41 — 2026-10-23

**问题（对 Q40 方法的纠正）：**
要 trace 一切 input/output，**肯定包括 hooks**（不是专门谈「trace hooks」，而是 hooks 本就是 output 的一部分）。如果用 agent 去 trace，一定会陷入死循环（agent 记录自己的记录动作→又被记录→∞）。你要跳出 agent 去想——大概是「建一个独立进程，监听 agent 然后捕获信息」。

**答案：**

核心：记录器必须**活在 agent 之外**（独立观察者进程）。若让 agent 自己写 trace，每次记录动作都是新的 agent 动作需被记录，无限回归。hooks 虽已是 IDE 跑的外部命令（不在 agent 工具流内），但更干净的做法是你说的**独立守护进程（daemon/sidecar）监听 agent 并捕获，agent 自身从不写 trace**。

### 一、进程外记录器设计

1. **Daemon（观察者）= trace 唯一写入者。** 长驻进程（launchd 或首个 hook 拉起），监听 Unix domain socket（`/tmp/session_recorder_<sid>.sock`）或命名管道；收事件 JSON 行，序列化进 `session_trace/{session_id}.jsonl`（单调序号 + 墙上时钟 ts）。因是独立进程，它对 trace 的写是 OS 文件 I/O，agent 不控制也不视为自身工具调用 → 无回归。
2. **Feeders（hooks）= 外部命令，非 agent 工具。** `.codebuddy/settings.json` 的 `UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop` 各调一个微命令 `recorder_feed --event X`，连 socket 把 payload 发 daemon。这些是 IDE 跑的命令，永远不是 agent 工具调用。捕获：用户 prompt、每个工具调用（skill/web/文件/命令）、以及**hooks 自身**——每次 hook 触发即一次 feeder 调用，daemon 记成 `{kind:"hook", name:"PostToolUse", payload, ts}`。hooks 被捕获正是因为外部+被观察，而非 agent 去记。
3. **被动 watcher（「监听 agent」那部分）。** daemon 用 macOS `kqueue`/`fsevents` 看 CodeBuddy 自身会话 transcript 文件（若有持久化）及 `turn_gate` 的 `.turn` 状态目录，被动观察 agent 实际写了什么 + hook 副作用（如 `turn_gate` exit 2 拦截），无需 agent 参与——最接近「录下含 hook 效应的一切」。

### 二、为什么逃出死循环

daemon 是**唯一写入者**。没有任何机制把 daemon 自己的写回灌进 agent 工具流，故不存在「log the log」无限。agent 是被记录者，从不记录自己。反例：agent 侧 logger 调工具 append → 该 append 是 agent 动作 → 须被记 → 记这个记 → ∞。

### 三、hooks 怎么被捕获（用户要点）

hook 触发只是一次外部命令执行；daemon 把每次触发记成一等事件。hook 的**效应**（如 `turn_gate` 拦写、写 `.turn` 状态）经 feeder 上报 exit code、或 watcher 观察产物捕获。hooks 天然是 output 流的一部分，不是特例。

### 四、第 0 步（须实测）

- daemon 可靠启动且与 hooks 共享 socket 路径。
- 各 CodeBuddy hook payload 实际携带：prompt 文本？tool output？reasoning？
- CodeBuddy 是否持久化会话 transcript 文件可 tail（最完整来源）。

架构在 macOS 今天即可落地；未知项只是 CodeBuddy 的 payload/transcript 细节，非架构问题。
