## Q34 — 2026-10-15
**问题：** D3 记录规范里那套 frontmatter（`revision`/`supersedes`/`change_summary`/`aux_files`）和 append-only 的 `supersedes` 修订机制，是不是过度设计？我有没有让你设计这个？如果有，我哪条具体指示告诉你要记录这个？你看看 `questions/` 文件夹下面每个 md 文件（比如 033.md），你看到有 `revision`/`supersedes` 这些东西吗？

**答案：**

### 1. 是不是过度设计？是。

D3 里我加的两块东西——① 记录文件头 frontmatter 强制带 `revision`/`supersedes`/`change_summary`/`aux_files`；② "改记录不就地改、追加新序号文件、用 `supersedes` 链指向上一版"的 append-only 修订机制——都是多余的。

### 2. 你有没有让我设计这个？没有。

你的蓝图只规定了四件事：
- 目录格式（`custom/{feature}/{number}_{topic}.md` + 可选的 `{number}_{topic}/` 辅助目录）；
- `register-custom-feature` 注册机制（写进 `custom_categories.json`）；
- 受管文件必须含 `custom/`，且改动留痕；
- 任一 feature 更新要同步 `{feature}_TOC.md` 与 `{feature}_index.json`。

通篇没有任何一处提到"每条记录要有 frontmatter""要带 revision""要 supersedes 链""改了要追加新版本"。你只说了"对某些 feature 做**有序记录**"——"有序"两字已经被目录格式里的**编号文件名**（`001-`、`002-`…）满足了，不需要再叠一套版本链。

### 3. 哪条具体指示告诉我"要记录这个"？没有。

关于"记录"唯一的具体指示，就是你蓝图第 1 点里的目录格式：记录是一个**以序号开头的 md 文件**，需要补充文件时用**同名辅助目录**。这就是记录的形态，仅此而已。frontmatter 字段和 `supersedes` 修订链是我自己脑补出来的"通用记录 schema"，不是你要求的。

### 4. `questions/` 文件夹的实证

`questions/033.md`（以及 029/030/031/032 等）的实际形态：

```
## Q33 — 2026-10-15
**问题：** …
**答案：** …
```

纯 markdown，没有 frontmatter，没有 `revision`，没有 `supersedes`。grep 整个 `questions/` 命中的 3 处 `supersedes` 和 1 处 `revision`，全是我在答案**正文里描述 008 设计**时写到的字，不是 questions 文件自己的元数据。

也就是说：**本项目自己的记录格式（questions/）比我在 D3 里强加的还要轻**——连 frontmatter 都没有。D3 却给 custom feature 的记录套了一层 questions/ 根本不用的 schema，既没被你要求，又和本项目的真实实践不一致。

### 5. 结论

- "有序记录"已由 D2 的**编号文件名**完全满足，无需额外版本机制。
- D3 应剥离 frontmatter（`revision`/`supersedes`/`change_summary`/`aux_files`）与 append-only `supersedes` 修订机制，记录回归为 D2 规定的"编号 md 文件 + 可选同名辅助目录"，与 `questions/` 的实践一致。
- `<feature>_index.json` / `<feature>_TOC.md` 的同步（D4）负责可发现性，不需要靠 frontmatter 字段去喂。

注：这与 Q30/Q32 同一原则——加字段/机制前先算维护成本，不为假想需求加配置项；这里连"假想需求"都没有，纯粹是我多写了一套。
