## Q5 — 2026-10-03
**问题：** 目前采用的 append-only `history.json` 方式，会不会对 AI coding 不太友好？因为 AI coding 每次都要先扫描一遍文件，然后 append？这样的话当 append 越来越多的时候，会减慢速度？

**答案（讨论，未改动 skill/脚本）：**
你的担心抓住了真问题，但要分两层看：**机械层面的 append 不会变慢，真正会变贵的是 AI 读历史的上下文成本。**

1. **append 本身不会变慢（机械/磁盘层）**：`append_history.py append` 是「读文件 → 解析 JSON → 压入新事件 → 写回」的纯磁盘 I/O。文件从几 KB 长到几 MB，磁盘操作成本可忽略；且这一步由脚本完成，**模型不需要把整份内容装进上下文**。所以「每次先扫描全文件再 append 会变慢」在性能层面基本不成立。

2. **真正的问题：上下文 / token 成本（AI 友好性层）**：AI coding 的瓶颈不是磁盘，而是**上下文窗口与每 token 计费**。如果每次 agent 处理 plan 时都把整个 `history.json` 读进 prompt，token 消耗随历史**线性增长**。8 个 event 时无所谓；但真实项目跑一两年、几百上千 event，每次都把几十 KB 的 JSON 灌进上下文，既浪费 token 也挤占有限的上下文窗口——这才是「对 AI coding 不友好」的实情。

3. **其实已有缓解，但不够彻底**：
   - 脚本的 `show` 子命令只打印「类型/时间/作者」摘要，模型本可以只看这个摘要而不读全文；
   - `questions.md` / `history_meta.json` 已是 companion 文件，把「问答」和「plan 元信息」从主日志分流，避免为这类信息读全量。

4. **更彻底的设计建议（不破坏 append-only）**：把 `history.json` 当作**只增不改的「真相源 / canonical log」**，再额外维护一个**可派生的轻量索引 / cache**，让 AI「想 append 或看当前状态」时不必读全量：
   - 维护一个 `_index.json`（或 `state.json`）：只存「最新 `event_id`、最近 N 条摘要、当前 plan 状态指针」；
   - 索引可由 canonical log **重新生成（rebuild）**，所以它本身不算「历史」、不要求只增不改，也就不与审计可信性冲突；
   - agent 默认读 `_index.json`（小、快），只有需要追溯细节时才按需读 `history.json` 的尾部 `tail` 或某条指定 event；
   - 这相当于给 append-only 日志加了一层「可被丢弃重建的缓存层」，把**可信性（append-only）**与**读取效率（轻量索引）**解耦。

5. **取舍小结**：append-only 为的是**可审计 / 可追溯（信任）**，AI 友好为的是**省 token / 省上下文（效率）**。两者并不矛盾——让日志保持只增不改作为真相源，把高频读取交给可重建的轻量索引即可。这也契合你之前「顶层 meta 另建 `history_meta.json`」的方向：meta 与索引本就是给「机读 / AI 读」用的旁路，而非审计主体。
