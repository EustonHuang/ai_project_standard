## Q21 — 2026-10-04
**问题：** 这东西越看越不像一个 skill，而更像一套「项目规范」——每个项目都要遵从 history update、folder structure、questions、issues 等记录方式；而且这套规范本身也得符合自己的规范（dogfooding），规范还在不断迭代，所以 architecture 里的 001/002/003 其实就是这套规范的版本。还有两点别扭/要厘清的：

1. **hook 的归属别扭**：我写 hook 时，hook 是**项目层**的（放在 `<workspace>/.codebuddy/settings.json`），但引用的文件是 **skill 层**的。这很别扭。如果不把它当 skill、而当成「所有项目都要遵从的项目规范」，那它就该存在于**能被所有项目引用的全局位置**（不是 `<workspace>/.codebuddy/...`，而是一个全局一处）。
2. **两条版本轴要分开**：每个项目（包括规范自身）都应声明**当前使用的项目规范版本**；同时每个项目拥有**自己的项目版本**，二者不能混。比如 euston_wiki 项目会有自己的迭代（wiki schema 更新等），但它所用的规范版本可能就是最新的 003——「项目所用规范版本」和「项目自身版本」是两个不同的轴。

**答案（我的看法）：基本同意，这是从 skill 升级为「元规范（metastandard）」的必然演化。核心是三点：**

**① 定位：skill → 全局项目规范（standard）。**
"skill" 暗示「某个 workspace 的 .codebuddy/skills 里一份可选的能力」。但这里定义的是「一切项目该怎么记历史」的强制约定，且自身也用同一套格式记历史（dogfooding）——这已经是**元规范**，不是 skill。architecture 001/002/003 正是这条规范的版本号，定位是对的，只是「skill」这个壳错了。

**② 全局位置 + 全局 hook，消除「项目层 hook 引用 skill 层文件」的别扭。**
当前 `<workspace>/.codebuddy/settings.json` 的 hook 指向 `$CODEBUDDY_PROJECT_DIR/.codebuddy/skills/.../scripts/turn_gate.py`，本质是把「全局约定」用「每项目各抄一份 hook」实现——重复且非单一可信源。正确做法：
- 把这套东西移到**全局一处**（如 `~/.codebuddy/global-skills/plan-history-standard/`，或一个 homedir 管理的 repo）；脚本路径用全局绝对路径或 `$PLAN_HISTORY_HOME` 环境变量，使所有项目共享**同一份安装、同一真相源**。
- hook 本身应**全局注册**（用户级 settings/hooks，一次安装对所有项目生效），而不是复制到每个 workspace。若 CodeBuddy 仅支持项目级 settings.json，则提供一个 bootstrap/install 步骤统一写入，避免各项目分叉。

**③ 两条版本轴必须分离（最关键点）。**
- **规范版本轴（standard_version）**：项目「所用规范的版本」，如 003。每个项目在根目录声明一份轻量标记（建议 `.plan-history/standard_version` 或 `project_standard.json`，含 `standard_version` + 是否锁定自动升级 `pinned`）。规范自己的仓库也声明它——它 dogfood 自己，所以自身 `standard_version=003`，且它自己的 `architecture/001..003.md` 既是规范版本、也是它的领域内容（二者重合，注明即可）。
- **项目自身版本轴**：项目的领域迭代（如 euston_wiki 的 wiki schema 版本、某产品的 release 版本）。项目自己的 `architecture/` 放的是**项目领域**的设计版本（v1/v2…），用已有的 `implemented_version`/`latest_version` 跟踪——但现在这条轴是「项目领域版本」，不再是「规范版本」。
- **数据模型**：把 `standard_version` 从 `architecture_index.json` 里拎出来单独存（它是「我遵守哪版规范」，不是「我的设计文档到哪版」）。`architecture_index.json` 的 `implemented/latest_version` 保留给**项目领域**版本。这样两个轴不混：`standard_version=003`（规范轴）独立于 `architecture/` 的 v-N（项目轴）。

**需要确认的点（不是建议，是落地前必须定的）：**
- **全局位置具体选哪**（homedir global-skills vs 独立 repo vs dotfiles），这决定 hook 路径怎么写、install 怎么做——这是真正要你拍板的。
- **CodeBuddy 是否支持用户级 hooks（全局生效）？** 如果有，hook 放用户级，彻底不用每项目抄；如果没有，需要 bootstrap 脚本统一注入。

**可选的（先不着急，等上面定了再说）：**
- 是否需要「规范版本自动升级检测」（项目声明 `pinned=latest` 时，工具提示有新规范版本）——锦上添花，不是 must-do。

**补充追问（2026-10-04，针对上一轮回答的 comments）：**

1. **② 的位置不该再叫 skills**：你给的 `~/.codebuddy/global-skills/plan-history-standard/` 本质上还是把它塞进 skills 下面，但我们已经定了它不是一个 skill，而是一套「项目规范框架」。它是**可选采用**的——至少你自己的项目要遵循，别人的项目可以不采用（别人有别人的框架）。所以每个项目有权采用或不采用；一旦采用，就要知道自己用的是哪个版本、最新是多少，并在不是最新时被提醒升级。

**答案（补充，同意并细化）：**

- **② 重定位：从「全局 skills」改为「独立框架仓库」**。我上轮把它放进 `global-skills/` 仍是 skill 思维，错了。正确模型是：框架 = **单一可信源的独立 repo**（git + GitHub remote）；采用方项目只持有一份 `standard_version` **锁文件（指针）**，不持有框架副本。框架提供工具去查「latest = ?」并在采用方落后时告警——这正是你第 1 点要的「采用后知版本、知最新、被提醒」。
- **git 是 004 的硬约束**。002 被覆盖 = 没有对「规范自身」做版本控制的直接后果。规则：**004 起，框架仓库每次版本 bump 必须 commit 并 push 到 GitHub remote**，每个 `architecture/NNN.md` 是一个打 tag 的版本，可随时 `git checkout` 还原「v002 当时写了什么」。同时采用方的 `standard_version` 锁文件也提交进**它自己的 git**，这样还能看到它何时升级。
- **独立 repo + 内置 skills（安装/更新/检查）**。框架仓库自带技能，作用于采用方项目：
  - `install-standard <version> <project>`：把指定版本框架装进目标项目（写 hook、写 `standard_version` 锁文件、脚手架目录结构）。
  - `update-standard <project> [--to latest|<version>]`：升级采用方的 `standard_version`，必要时更新 hook，并标注版本间 breaking change。
  - `check-standard <project>`：报告当前 vs 最新，落后则告警。
  - 这些 skill 就放在框架仓库内（dogfooding：框架自己的仓库也用它们、也以自己为规范）。
- **顺带解决最初的别扭**：原「项目层 hook 引用 skill 层文件」之所以别扭，是因为框架被当成了某个 workspace 的 `.codebuddy/skills` 子目录。改成独立 repo + `install-standard` 由 skill 把 hook 写进采用方、指向**已安装的框架路径**后，这个别扭消失。

**需要确认的点（推进 004 前必须定）：**
- 框架仓库的 GitHub 位置（org/repo 名）与 `standard_version` 锁文件格式（如 `.plan-standard/version` 或 `project_standard.json`）。
- 首批要交付的 skill 范围：`install/update/check` 三个是否就是 must-have（我认为是）。
- 框架**版本间的 breaking-change 策略**：`update-standard` 遇到非向后兼容变更怎么办（建议类 semver：major=breaking，须人工 review）。
