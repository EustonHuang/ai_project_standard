## Q43 — 2026-10-23

**问题（对 Q42 设计的两点质疑）：**
1. 你的设计为什么还在用 hook？2. 你说看 `.turn` 状态，为什么有帮助？

**答案：**

### 一、为什么仍用 hook（边界澄清）

记录器是 **daemon，完全在 agent 之外**。hook 不是 agent 自己记录，而是 **IDE 外部运行的命令**。链路：agent 动作 → IDE 触发 hook → feeder 命令（外部）把 payload 转发给 daemon socket → daemon 写 trace。agent 从不调 hook、从不写 trace；feeder 的 socket 写是外部进程的 OS I/O，**不是 agent 工具调用**，不会被回灌为 agent 动作 → 无死循环。这正是「跳脱 agent」：hook 只是 IDE 向外界通知事件的通道，不是记录器本身。

为何用 hook（而非纯 watching）：daemon 必须「得知」事件。两通道：
- **hook（push）**：IDE 唯一实时结构化推送，能拿到 prompt 原文、工具名、input/output。
- **watcher（pull）**：只看落盘内容；除非 CodeBuddy 把 prompt/工具输入持久化到文件，否则拿不到逐字 prompt 与工具输入。

故 hook 是可靠的_structured_推送源，watcher 是被动交叉校验。hooks 作为「output 一部分」也被满足：每次 hook 触发即 daemon 记下的 `{kind:"hook",...}` 事件。

能否去掉 hook？**能——若** CodeBuddy 暴露一份完整结构化会话 transcript 可 tail（含 prompt+工具调用+IDE/hook 事件），则纯 watching 即可、更干净。此为第 0 步待测项；未确认前 hook 是稳妥选择。设计不*依赖* hook，只是兜底推送。

### 二、为何看 `.turn` 状态有帮助

`.turn/{session}.json` 是 `turn_gate` 的**持久化每会话状态**（代码 L31 `TURN_DIR=.codebuddy/hooks/.turn`、L46 状态文件、L60 原子写）：记录 gate 实际做了什么——`declared`（本轮记账的文件）、`baseline_max_id` 等。watcher 观察它 = 把 **hook 副作用作为 ground truth 捕获**，且不依赖 hook payload 是否送达 daemon：
- `turn_gate record` 记账某文件 → `declared` 在磁盘增长 → 即使该 hook 的 feed 消息丢失，watcher 仍可见。
- `end` gate 拦写（exit 2）→ 该强制动作留痕，watcher 可佐证。

故 `.turn` 是 gate 强制行为的**交叉校验/审计产物**；既然要录「含 hook 效应的一切」，gate 动作本就是 output 一部分。注意：`.turn` 单独给不了 prompt/工具输入，它**补充** hook 推送+transcript，专捕 gate 行为，非替代。

**结论：** hook=事件结构化推送（含 hook 自身触发）；`.turn` watcher=被动捕获 gate 落盘副作用作安全网。二者同喂进程外 daemon，agent 始终在记录循环之外。
