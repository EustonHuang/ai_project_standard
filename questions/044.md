## Q44 — 2026-10-24

**问题（对 Q42/Q43 设计的两点精确追问）：**
1. `agent 动作 → IDE 触发 hook`，这个 hook 是 agent 动作的第一步吗？2. 这个 hook 本身不会被记录，对吧？

**答案：**

### 一、hook 是不是 agent 动作的第一步？——不是

hook 是 **IDE 在 agent 工具执行「前后」触发的外部通知**，不是 agent 自己的一步。一个工具调用的真实时序：

1. agent 内部决定调用工具 T（推理/决策；不是 hook，也不可直接作为 hook 捕获，除非 agent 自发射 `reasoning`）；
2. IDE 触发 `PreToolUse(T)`：工具执行**前**，外部命令，可拦截（exit≠0）；
3. 工具 T 真正执行：写文件/web search 等，才是 agent 动作的实际效果；
4. IDE 触发 `PostToolUse(T, result)`：工具执行**后**，外部命令，看结果。

故 hook 是**包住 agent 工具执行的外层包装**，由 IDE 触发，不属于 agent 动作本身。`PreToolUse` 虽在工具效果前发生，但是 IDE 的门，不是 agent 的步骤。

### 二、hook 本身不会被记录？——纠正：事件级会被记录

用户原始要求「tracing 一切包括 hooks」，故本设计**记录 hook 事件**，非忽略：
- `UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop` 每次触发，feeder 把「该 hook 触发 + payload」发 daemon → 写 trace 成 `{kind:"hook", name, payload, ts}`。hook 事件与 payload 皆录，即「hooks 是 output 一部分」。
- hook 副作用（turn_gate 记账文件、exit 2 拦写）经 `.turn` watcher 亦录。

**唯一不录的是记录器自身的管道**：`recorder_feed` 进程运行、其 stdout 等——那是记录器自己，再观察它即用户警告的死循环；靠「daemon 不回灌自身写」避开。

准确结论：
- **hook 事件** → ✓ 录（hooks-in-output）；
- **记录器自身机理**（feeder 进程内部）→ ✗ 不录（防循环）。
用户「hook 不会被记录」只对「记录器 plumbing」成立，对「hook 事件」不成立——本设计恰恰录了 hook 事件。
