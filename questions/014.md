## Q14 — 2026-10-04
**问题：** 既然人或 agent 只写内容、索引与 TOC 由脚本派生，而链接对人和阅读很友好，那保留 TOC 是可行的。进一步：除了 questions，architecture / history / issues 也应该引入 TOC 方便人查找。但"如何写 TOC"需要给个方案。请记入 questions。

**答案（讨论，未执行）：**
同意保留并扩展到四类。下面是 TOC 方案（只列主要项）：

**1. 命名与位置：** 每个板块一个 `<kind>_TOC.md`，放在 **plan 根**（与 `*_index.json` 同级，沿用"索引/元信息在根好找"的既定规则）：
- `architecture_TOC.md`、`history_TOC.md`、`questions_TOC.md`、`issues_TOC.md`。

**2. 内容形态（markdown + 相对链接）：**
- 顶部注释：`<!-- 自动生成，请勿手改；改动会被脚本覆盖 -->`。
- 每项：`[label](相对路径) — 一句摘要`，摘要来自 `*_index.json` 的 brief：
  - history：`[001 · plan_created · 2026-10-03](history/001.json) — <change_summary>`
  - architecture：`[v001 · 初版设计](architecture/001.md) — 状态：已落地`
  - questions：`[Q1 · <问题>](questions/001.md) — <answer_summary>`
  - issues：`[001 · collision · open](issues/001/description.json) — <description>`
- 相对链接保证在编辑器/GitHub 可点跳转。

**3. 生成方式（脚本派生，不手改）：**
- 新增子命令 `gen-toc --plan DIR [--kind all|history|...]`：从各 `*_index.json` 渲染对应 TOC。
- `append` 时**自动顺带重生成对应板块的 TOC**（索引已更新，渲染只多一次文件写，成本极低），保证 TOC 与索引一致、始终新鲜。
- 人随时可 `gen-toc` 手动全量刷新。

**4. 长度控制（防 TOC 自身膨胀）：**
- TOC 是给人看的总览，只对**最近 N 条**出链（如最近 200），末尾注明"更早记录见 `history/NNN.json` 或 `history_index.json`"，避免超长计划下 TOC 也变巨文件。
- 机器检索仍走 `*_index.json`（不读 TOC），TOC 截断不影响程序化查找。

**5. 与既有的关系：** TOC = 索引的人类可读渲染，**同源**（都来自 `*_index.json`，单一真相源）。索引负责"机器高效读/写"，TOC 负责"人类点链接浏览"，二者由脚本从同一份 index 派生，不会分叉。

**结论：** 四类各一个 `<kind>_TOC.md`（plan 根、相对链接、自动生成、可截断），由新子命令 `gen-toc` 生成、`append` 时自动刷新。属设计补充，应作为 architecture 下一版本的 delta 记录；本轮仅记录问答，未改脚本/计划/文件。
