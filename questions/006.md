## Q6 — 2026-10-03
**问题：** 所以，AI coding 在执行 append 的时候，是怎样的流程？他们真的是读了 `history.json` 以及 `questions.md` 的所有的内容吗？

**答案（讨论，未改动 skill/脚本）：**
AI coding 执行 append 时，**并不必然**把两个文件全读进上下文。拆开看：

1. **`history.json` 的重活在脚本，不在模型**：按本 skill 设计，append 是模型根据**当前对话上下文**组合一个小 event 对象，再调 `append_history.py append`；脚本在磁盘上完成「读→解析→压入→写回」并自动补 `event_id`/`schema_version`/`recorded_at`/`plan_state_snapshot`。模型全程不需要把整个 `history.json` 装进上下文，甚至不需要知道当前最大 `event_id`（脚本自动算）。

2. **模型真正会读的是"指令"不是"数据"**：它读 `SKILL.md` / `references` / `workflow`（规则说明，体积小、只读一次、不随历史增长）以知道"调哪个脚本、event 长什么样"；不会为 append 去读历史数据本身。

3. **`questions.md` 才是通常会被全读的文件**：追加一节 Q&A 时模型一般先读它（markdown，比 JSON 日志小、且给人看）以确认格式与追加位置再编辑。这一步确有"一次全读"，成本随问答条数线性增长，但纯文本、通常远小于 `history.json`，且只在"有新问题要记"时读，非每次动作都读。

4. **你担心的"每次扫描全文件"是可能但非必然，且本 skill 已在规避**：脚本 append（history.json 不进上下文）、`show` 摘要（不读全文）、companion 分流（问答/元信息另存）三者共同把成本降到最低。

5. **真正的成本边界**：只有当 agent **主动选择**把 `history.json` 整份读进上下文（如为决策理解 prior events）时，才出现线性膨胀——这是"使用方式"问题，非 append 机制代价；缓解即 Q5 提的"可重建轻量索引 `_index.json`"：agent 默认读小索引，仅在追溯细节时按需读某条 event。

**小结**：正确姿势是"模型出 event、脚本落盘"，`history.json` 不必进上下文；`questions.md` 因追加需要通常全读一次，但体量小、频率低。瓶颈在"模型是否全读主日志"，本 skill 设计已把该成本压到最低。
