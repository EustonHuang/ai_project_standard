## Q42 — 2026-10-23

**问题：**
把 Q38–Q41 的整段讨论收口：到底怎么把 CodeBuddy session 的一切（prompt/回答/thinking/skill/文件/web/hook/输出）录下来？作为结论记进 questions。

**答案：**

经 Q39（框架不能全录）→ Q40（给方法：独立 hook 记录器）→ Q41（agent 自录会死循环，须进程外 daemon）三次纠正，收敛设计如下。

### 一、最终架构（进程外观察者）

- **Daemon（唯一写入者）**：独立长驻进程，监听 Unix domain socket，把事件序列化进 `session_trace/{session_id}.jsonl`（单调序号 + 墙上时钟 ts）。活在 agent 外 → agent 从不写 trace → 无 log-the-log 死循环。
- **Feeders（hooks 作外部命令）**：`UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop` 各调 `recorder_feed --event X` 连 socket 发 payload。捕获 prompt、每个工具调用（skill/web/文件/命令），以及 **hooks 自身触发**（记成 `{kind:"hook", name, payload, ts}`）。
- **Watcher（被动监听）**：macOS `kqueue`/`fsevents` 看 CodeBuddy 会话 transcript 文件（若有）与 `turn_gate` 的 `.turn` 状态，被动捕获 agent 实际输出与 hook 副作用（如 `turn_gate` exit 2 拦截）。

### 二、难点处理

- **thinking**：原始隐藏推理仅当平台暴露才可捕；否则要求 agent 边做边发 `reasoning` 条目（陈述式，非原始 CoT）。
- **agent 回答正文**：transcript 拷贝 或 agent 自发射。
- **hooks**：外部命令，触发即被 daemon 记，天然是 output 一部分。

### 三、与 ai-project-standard 的关系

本记录器**独立于** history 框架（那是轻量溯源）。history 事件可引用 trace 路径，不内嵌逐字正文，避免膨胀。

### 四、落地前须实测（第 0 步）

1. daemon 可靠启动且 hooks 共享 socket 路径；
2. 各 hook payload 实际携带（prompt 文本？tool output？reasoning？）；
3. CodeBuddy 是否持久化会话 transcript 文件可 tail（最完整来源）。

### 五、产出形态（待批准实现）

`skills/session-recorder/`：daemon 脚本 + `recorder_feed` + `.codebuddy/settings.json` 接线 + watcher。按纪律先出方案再实现。
