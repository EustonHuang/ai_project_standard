# IMP-003 · 历史记录必须携带产生它的 standard_version（版本可追溯）

## 背景
当前 `history/NNN.json` 事件与 `history_index.json` 的 brief 都**不记录**该条记录是基于哪个 `ai_project_standard` 版本产生的。版本信息只在 Adopt 事件（事件 1）的自由文本里顺带提了一句 v0.5，且结构体里没有 `standard_version` 字段。

项目根目录的 `standard_version` 文件（`standard_version=v0.5`、`pinned=latest`）只是**单个当前锁**，记录「此刻项目钉在哪个版本」，并不等于「每条历史记录当初在哪个版本下产生」。一旦用户升级框架（如 v0.5 → v0.6），`standard_version` 文件变为新版本，会话开始注入的规则也随之更新——但**历史记录本身无法回溯到产生它的规范版本**，未来的新事件也不会自动打上「基于 v0.6」标记。这导致版本升级后，history 里的每一条修改都失去了「依据哪一版标准」的上下文。

## 改进点（下个框架版本）
在 `history/NNN.json` 事件 schema 中新增结构化字段 `standard_version`；`append_history.py` 在落盘每条事件时，从项目根 `standard_version` 文件读取当前版本值并**写入该字段**（快照语义，写入后不再随后续升级改变）。

建议同时：
- 在 `history_index.json` 的每条 brief 中也加入 `standard_version`（取值与对应事件一致），使索引层即可按版本过滤/审计，无需回读每个事件体；
- `references/workflow.md` 的「记录规范」节说明该字段由脚本自动注入、禁止手填、代表「本事件产生时所依据的框架版本」。

## 实现要点（落地方向）
- `append_history.py`：记录前 `read` 项目根 `standard_version`（`standard_version=<ver>` 行），注入事件体 `standard_version` 字段；生成 `history_index.json` brief 时一并带出。
- schema 文档（`references/` 或事件模板）增加该字段说明，示例：

```json
{
  "event_id": 18,
  "standard_version": "v0.5",
  "event_type": "plan_modified",
  ...
}
```

- 升级框架（install-standard 写入新版本）后，新事件自然带新版本号；旧事件保留旧版本号，实现逐条可追溯。

## 范围界定
- **必须**：事件体 `standard_version` 字段 + 脚本自动注入。
- **建议**：索引 brief 同步带版本，便于审计。
- 不影响 `standard_version` 文件本身的「当前锁」语义，二者职责分离（前者=逐条快照，后者=当前钉版）。

## 关联
- euston_wiki `standard_version` 文件（当前锁 v0.5）
- euston_wiki `history_index.json` 与 `history/*.json`（现状：无版本字段）
- 与 IMP-001（编辑质量守卫）、IMP-002（执行后 commit）同属采纳方项目实测暴露的框架缺口
