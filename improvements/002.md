# IMP-002 · 执行 architecture plan 后必须 commit（发布动作联动）

## 背景
在采纳方项目 euston_wiki 执行 architecture/002（Wiki 知识库数据库设计）时，agent 只做了本地文件改动 + 本地 history 留痕（append_history.py + turn_gate 强检），没有触发任何 git commit / push / tag。直到用户显式要求才发布。用户在 Q5 追问「执行完毕后为何没有自动 push/tag、是否应联动」，据此提出本改进：仅当 implement 了一个 architecture（执行 plan）时，agent 才应联动 `git commit` + `git push` 将执行产物发布到远端；普通 bookkeeping 改动不提交。

## 改进点（下个框架版本）
**仅当**某个 architecture 版本（plan）被「执行/落地」（产生工程文件改动，或 `set-implemented` 翻转 `implemented_version`）时，标准**必须**要求一次**完整的发布动作链**：`git commit` → `git push` → `git tag`，三者**全部强制、紧跟执行、不可拆分、不可延迟**；其余情形（改进提案 / correction / 问答等 bookkeeping）绝不触发任何提交 / 推送 / 打标。

建议实现方式（在 `set-implemented` 命令内自带，连做）：
- `git add -A && git commit`（commit message 约定 `implement architecture/NNN: <title>`）；
- 紧接 `git push`（推送当前分支到远端）；
- 紧接 `git tag v{NNN}`（tag 版本号 = 被 `set-implemented` 翻转的那个 architecture 版本号，例如 `set-implemented --version 3` → 打 `v3`），随后 `git push --tags` 推送标签；
- 即一次性执行：`git add -A && git commit -m "implement architecture/NNN: <title>" && git push && git tag v{NNN} && git push --tags`。

## 范围界定（发布纪律）
- **唯一触发条件**：仅当「implement 了一个 architecture（执行/落地某个 plan，或 `set-implemented` 翻转 `implemented_version`）」时，agent 才允许且**必须**执行发布链 `git commit` → `git push` → `git tag v{NNN}`（`NNN` = 被实现的 architecture 版本号），三者紧跟、连做不拆分；tag 版本号严格等于 architecture 注明的版本号。
- **禁止（agent 不得擅自）**：改进提案 / correction / 问答（Q&A）等 bookkeeping 改动，agent **不得** commit、不得 push、更不得打 tag；须保持在未提交的工作区状态供用户审阅，确需提交时先询问。
- **反例（已被纠正）**：agent 曾把改进提案、纠错记录等 bookkeeping 擅自 commit 并 push，违反本纪律。另：本改进早期草案曾把 push/tag 写成「交由用户显式触发 / 可选扩展」，已被明确推翻——**implement 场景下 push 与 tag 必须紧跟 commit 自动执行，不允许延迟或留给用户手动触发**。
